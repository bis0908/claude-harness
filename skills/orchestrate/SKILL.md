> **구현·분석 에이전트 주의.** 이 골격은 검증·학습·추적·조율 역할(qa-guard, evaluator, design-reviewer, milestone-tracker, plan-auditor, compound-learner, tdd-agent, refactor-specialist, bug-fixer)만 포함한다. 실제 코드를 작성하는 **구현 에이전트**(프론트·백엔드/DB·API)와 **레거시 분석 에이전트**는 프로젝트가 정의한다. Next.js + MySQL 스택 예시는 `examples/nextjs-mysql/`(page-builder·data-layer·legacy-reader)를 복사·변형해 사용한다. 아래에서 "프론트 구현 에이전트", "백엔드 구현 에이전트", "레거시 분석 에이전트"는 이 프로젝트 정의 에이전트를 가리킨다.

> **역할 → 실제 에이전트 이름 바인딩 (필수).** 오케스트레이터는 아래 3개 역할명으로 구현·분석 에이전트를 호출하지만, `Agent()` 호출 시에는 **역할명이 아니라 이 표에서 해소한 실제 에이전트 이름**을 넘긴다. 각 프로젝트는 역할↔실제 이름 매핑을 선언한다 — 프로젝트 `CLAUDE.md` 에 1줄 매핑표를 두는 것을 권장한다. 선언이 없고 `examples/nextjs-mysql` 의 구현 에이전트를 그대로 설치했다면 아래 기본 바인딩을 사용한다. 둘 다 없으면 사용자에게 "이 역할을 수행할 실제 에이전트 이름"을 1회 확인한 뒤 진행한다.
>
> | 역할 | `examples/nextjs-mysql` 기본 | 이 프로젝트 실제 이름 |
> |---|---|---|
> | 프론트 구현 에이전트 | `page-builder` | (프로젝트가 선언) |
> | 백엔드 구현 에이전트 | `data-layer` | (프로젝트가 선언) |
> | 레거시 분석 에이전트 | `legacy-reader` | (프로젝트가 선언) |

## Phase 0: 컨텍스트 확인

작업 시작 전 현재 상태를 파악한다.

### 공통 실행 계약

이 스킬은 전체 파이프라인의 기준 규칙이다. 각 에이전트 문서는 역할과 입출력 책임만 정의하고, 세부 실행 절차는 해당 스킬을 우선한다.

모든 하위 에이전트 호출에는 아래 작업 봉투를 포함한다.

```markdown
## 작업 봉투

- 목표: <이번 호출에서 완료할 사용자 가치 1문장>
- 범위: <구현·검증 대상 파일 또는 기능 목록>
- 제외: <구현하지 않을 항목>
- 참조: <티켓, 레거시 분석, 디자인 레퍼런스, API 명세>
- 완료 기준: <검증 가능한 조건>
- 금지 사항: <이번 호출에서 절대 하지 않을 작업>
- 반환 형식: <표준 반환 형식>
```

작업 봉투에서 `목표`, `범위`, `완료 기준` 중 하나라도 비어 있으면 구현 에이전트를 호출하지 않는다. 오케스트레이터가 먼저 티켓 또는 문서를 다시 읽어 값을 채운다.

### 재발 방지 학습 푸시 (의무)

서브 에이전트가 SKILL.md 포인터를 스스로 따른다는 보장이 없으므로, 오케스트레이터가 강제 주입한다. 아래 에이전트를 호출할 때는 작업 봉투 `참조` 에 해당 카테고리 인덱스 경로를 **반드시 포함**하고, 봉투 본문에 다음 지시를 넣는다:

> 작업 시작 전 `docs/compound/{카테고리}/README.md` 를 읽고, 각 유형 파일 첫 줄 load-when 술어를 확인하여 현재 작업이 해당하는 사례 파일만 로드해 같은 실수를 반복하지 마라.

| 호출 에이전트 | 주입할 카테고리 인덱스 |
|---|---|
| 프론트 구현 에이전트 | `docs/compound/frontend/README.md` |
| 백엔드 구현 에이전트 | `docs/compound/data-layer/README.md` |
| evaluator | `docs/compound/evaluation/README.md` |
| qa-guard | `docs/compound/qa/README.md` |
| design-reviewer | `docs/compound/design/README.md` |
| 레거시 분석 에이전트 | `docs/compound/legacy/README.md` |
| bug-fixer | `docs/compound/bugfix/README.md` |
| tdd-agent | `docs/compound/tdd/README.md` |

`docs/compound/` 가 아직 없는 신규 프로젝트는 주입할 인덱스가 없으므로 이 단계를 건너뛴다 — compound-learner가 첫 학습 시 카테고리를 생성한다. 이 주입을 누락하면 자가개선 루프의 소비 단계가 끊긴다. 배경은 `docs/compound/README.md` 참조.

**size-on-read — curate-needed 플래그 적재 (작업 차단 없음).** 위 표대로 카테고리 `README.md` 를 작업 봉투 `참조` 에 주입할 때, 그 카테고리의 유형 파일 중 임계를 초과한 파일이 있으면 해당 경로를 **curate-needed 세션 메모**에 적재한다(현재 작업 흐름은 막지 않는다 — 읽기 비용이 곧 경제 신호다). 임계 기본값은 **150줄**(튜닝 가능)이다. 단, 사례 파일은 사례 1건이 매우 긴 단일 bullet 한 줄로 누적되는 형식이라 줄 수만으로는 신호가 약할 수 있다 — 줄 수 외에 카테고리 README "다루는 사례" 셀이 supersede 체인으로 비대해진 행도 임계 신호로 본다. 이 플래그는 Phase 5 드레인에서 소비된다.

**표준 반환 형식**

모든 구현·검증 에이전트는 아래 키를 유지한다. 해당 없는 항목은 `없음`으로 작성한다.

```markdown
완료 항목:
- <파일 또는 검증 항목>

미완료 항목:
- <없음 또는 항목>

확인 필요:
- <없음 또는 질문>

다음 단계:
- <오케스트레이터가 수행할 작업>

마일스톤: M{N}
단계: <phase>
에이전트: <agent-name>
```

### 입력 유형 분기

**가장 먼저** 사용자 입력이 다음 중 어느 유형인지 판별한다:

| 입력 유형 | 판별 기준 | 처리 경로 |
|-----------|----------|-----------|
| 마일스톤/기능 구현 요청 | "M3 작업", "사용자 목록 페이지 구현" 등 | Phase 0 나머지 → Phase 1~5 정상 파이프라인 |
| 리팩토링/구조 개선 요청 | "중복 제거", "함수 분리", "파일 정리", "이름 변경", "구조 개선" 등 | Phase R → `Agent(refactor-specialist)` → `Agent(qa-guard)` |
| **버그 증상 보고** | 에러 메시지, "안 됨", "깨짐", "안 보임", 스택트레이스 포함 | 아래 버그 경로로 즉시 이탈 |
| **재개 프롬프트 요청** | "다음 세션 프롬프트", "재개 프롬프트", "이어서 할 프롬프트", "handoff 프롬프트 만들어줘" 등 | 아래 재개 프롬프트 경로로 즉시 이탈 |
| **compound 정리/정돈 요청** | "compound 정리해줘", "재발방지 사례 정돈", "누적 학습 정리" 등 (버그 수정·기능 구현 아님) | 아래 compound-curate 온디맨드 경로로 즉시 이탈 |
| **계획 정합성 검증 요청** | "정합성 확인", "체크리스트 아직 유효한지", "계획 점검", "next step 계획 맞는지", "마일스톤 계획 검증" 등 (구현·버그 아님) | 아래 계획 정합성 감사 경로로 즉시 이탈 |

**버그 증상 보고 시 처리 경로:**
1. 오케스트레이터 파이프라인(Phase 1~5)을 실행하지 않는다
2. `Agent(bug-fixer)` 에이전트를 직접 호출하여 버그를 수정한다 (작업 봉투 `참조`에 `docs/compound/bugfix/README.md` 의무 포함 — 카테고리가 있으면. "재발 방지 학습 푸시" 표 참조)
3. **evaluator 게이팅 — 동작 레이어 경로-prefix 화이트리스트 판정.** bug-fixer 반환 메시지 `완료 항목`의 파일 목록을 추출하여, 프로젝트가 정의한 동작 레이어 화이트리스트 prefix 중 **하나라도 닿는지**만 본다. 판정은 경로 prefix 매칭 한 줄로만 수행한다 — "비즈니스 로직을 건드렸는가" 같은 의미 판단은 금지. 평가 깊이는 **skip / full 이진**이며 경량 evaluator 모드는 없다.

   ```
   동작 레이어 화이트리스트 (prefix) — 프로젝트가 정의. 일반 분류:
     데이터 접근 레이어   서비스 레이어   DB 접근   API 핸들러
     인증   세션
   (예시 경로 매핑은 examples/nextjs-mysql 또는 프로젝트 CLAUDE.md 참조)
   ```

   - **닿음** (완료 항목 중 위 분류에 매칭되는 파일이 1개 이상): `Agent(evaluator)` 를 호출하여 수정 결과가 원본 스펙을 충족하는지 검증한다 — bug-fixer 반환 메시지의 `완료 항목` 파일 목록과 수정 맥락(버그 증상, 원인)을 함께 전달한다 (작업 봉투 `참조`에 `docs/compound/evaluation/README.md` 의무 포함)
     - evaluator 승인 → 4번으로 진행
     - evaluator 미승인 → bug-fixer에 재수정 요청 → evaluator 재검증. 동일 미해결 항목이 2회 연속이면 stuck 판정 후 에스컬레이션 (파이프라인 stuck 기준과 동일)
   - **안 닿음** (완료 항목이 스타일 파일·컴포넌트 마크업·className/JSX-only 등 동작 레이어 외에만 한정): evaluator를 **스킵**한다. bug-fixer 자체 검증(qa-guard 계열)으로 충분하며, 무거운 3자 대조·브라우저 스모크 라운드트립을 생략한다. 곧바로 4번으로 진행한다.
   - **위험 주석**: className 리네임에 조건부 렌더 누락이 묻어드는 케이스가 있다 — 그래서 화이트리스트를 **엄격 적용**(prefix 매칭 외 임의 확대 금지)하여 동작 레이어가 닿으면 반드시 full evaluator로 잡는다.
4. **compound-learner 호출 게이트 — 사용자 시각 검증 분기.** evaluator 게이팅 결과에 따라 분기한다.
   - **evaluator 닿음 + approved**: evaluator가 동작 정합성을 보증했으므로 즉시 `Agent(compound-learner, 트리거: bug-fix, 보고서: bug-fixer 반환 메시지 전문, run_in_background: true)` 를 호출한다.
   - **evaluator 안 닿음** (스타일/마크업 단독, evaluator 스킵 케이스): compound-learner를 **즉시 호출하지 않는다**. 5번으로 진행해 사용자에게 시각 검증을 요청하고, 6번에서 사용자가 "확인됐다" 긍정 응답을 한 경우에만 compound-learner를 호출한다.
   - **이유**: 시각 결함은 사용자 시야가 단독 정보 소스다. bug-fixer 자체 검증은 코드 차원이라 "박스가 사라졌는지"를 확정할 수 없다. evaluator 스킵으로 비워진 검증 자리를 사용자 응답이 메우지 않으면, 잘못된 학습(1차 오진단을 정답으로 누적)이 영구 기록된다.
5. 사용자에게 bug-fixer 수정 내용 + evaluator 결과(또는 스킵)를 전달한다.
   - **게이팅 결정 로깅(의무)**: 보고에 `evaluator 게이팅: 닿음 — 매칭 경로 {prefix/파일}` 또는 `evaluator 게이팅: 안 닿음 — 동작 레이어 외 (스킵)` 를 **1줄 명시**한다. 회귀 가림을 사후 감사할 수 있도록 누락 금지.
   - **evaluator 닿음 경로**: 그대로 종료한다(compound-learner는 4번에서 이미 백그라운드 호출됨).
   - **evaluator 안 닿음 경로**: 종료하지 않고, "이 수정으로 시각 결함이 실제로 해결됐는지 브라우저에서 확인 부탁드립니다" 를 명시한 뒤 사용자 응답을 대기한다. **재발 방지 학습은 사용자 응답 후 6번에서 수행됨**도 함께 명시한다.
6. **사용자 시각 검증 응답 처리 (evaluator 안 닿음 경로에서만 실행).** 다음 턴에서 사용자가 보내는 응답에 따라 분기한다.
   - **긍정 응답** ("확인됐다", "해결됐다", "잘 됨", "오케이", "박스 사라짐" 등): `Agent(compound-learner, 트리거: bug-fix, 보고서: bug-fixer 반환 메시지 전문 + 사용자 시각 검증 결과, run_in_background: true)` 를 호출하고 종료한다. **이때 봉투에 "사용자 시각 검증 통과(응답 인용)"를 명시**하여 정답으로 누적되도록 한다.
   - **부정/미해결 응답** ("수정 안됨", "여전히 보임", "다른 곳도 동일" 등): compound-learner를 **호출하지 않는다**. 2번 bug-fixer 재호출 트랙으로 회귀하여 추가 진단·수정한다. 사용자 응답 본문(스크린샷·위치 추가 정보)을 새 bug-fixer 봉투의 `진단 맥락`에 포함한다. 재수정 후 다시 5번으로 진입한다.
   - **2회 이상 재수정이 누적된 경우**: 최종 긍정 응답 후 compound-learner 호출 시, 1차·2차 가설과 정진단 흐름을 봉투에 함께 전달하여 compound-learner가 자매 보존(둘 다 가치 있음) vs `_superseded` 격리(1차가 오진단으로 가치 없음) 를 판단하게 한다. 봉투에 "1차는 오진단이었다 — 격리 검토 권고" 또는 "1차는 a11y 보강으로 가치 보존" 의 판단 근거를 명시한다.

> 이유: 버그 수정은 마일스톤 파이프라인과 무관한 단발성 작업이다. 레거시 분석·design-reviewer 등 불필요한 에이전트를 호출하지 않는다. evaluator는 opus + 3자 대조 + 브라우저 스모크라는 무거운 검증이므로, 동작 레이어가 닿을 때만 실행하고 순수 시각/마크업 수정에는 생략하여 개입을 경제화한다. compound-learner 학습은 evaluator 닿음 케이스는 evaluator approved 가 검증을 대체하고, 안 닿음 케이스는 사용자 시각 검증이 그 자리를 메운다 — 두 경로 모두 검증된 정답만 누적되도록 게이트를 둔다.

> **예외 — 신규 인증/세션 설계가 섞인 버그 경로**: "버그 수정" 봉투로 들어왔어도 그 해결이 단순 코드 교정이 아니라 **신규 토큰·쿠키·세션 메커니즘 설계**(예: 임퍼소네이션 별도 쿠키, 자동로그인 재설계)를 요구하면 bug-fixer 단독으로 처리하지 않는다. ① 세션/쿠키 메커니즘(별도 쿠키 vs 기존 세션 변형, TTL, 서명 방식)을 사용자에게 1회 선결정 받고, ② `Agent(tdd-agent)` → `Agent(백엔드 구현 에이전트)` → `Agent(프론트 구현 에이전트)` 트랙으로 분리 호출한 뒤 evaluator·qa-guard·design-reviewer로 검증한다. 판별 기준: 수정이 새 쿠키명·새 토큰 발급/검증 함수·인증 분기 신설을 동반하면 단발 버그가 아니라 설계 작업이다.

### 컨텍스트 잔여량 감시 루프

각 Phase 시작 전과, 레거시 분석 / tdd-agent / 구현 에이전트 / design-reviewer / qa-guard / evaluator / plan-auditor 반환 직후에 컨텍스트 잔여량을 보수적으로 추정한다.

**1차 게이트 — 정량 임계 (이것이 유일한 정상 중단 트리거다):**

- 컨텍스트 윈도우는 150k 토큰으로 본다. 마진 10%를 적용해 **누적 사용량이 약 135k 토큰(잔여 ~15k, 10%)에 도달했을 때만** 재개 프롬프트를 동반한 안전 중단을 발동한다.
- 정확한 토큰값을 직접 읽을 수 없으므로, 다음 프록시를 135k 기준으로 보수적으로 환산해 추정한다. **개별 조건이 아니라 누적 사용량이 임계에 닿았는지로만 판단한다.**
  - 자동 컨텍스트 요약(compaction)이 이미 1회 이상 발생했다 → 거의 확실히 임계 근접.
  - 누적으로 연 파일·반환받은 에이전트 산출물의 총량이 길고, 직전 몇 턴 동안 응답·도구 결과가 지속적으로 길었다.
  - 위 신호가 약하면 아직 임계가 아니다 — **남은 Phase 수·반복 실패 횟수만으로는 중단하지 않는다.**
- **임계 미달이면 작업을 계속한다.** 남은 Phase·보완 루프가 2단계 이상 남아 있어도, 동일 실패가 반복돼도, 그 자체로는 중단 사유가 아니다.

**2차 보조 — 진행 불가 판정 (정량 게이트와 별개):**

- stuck 에스컬레이션(동일 FAIL 3회), 외부 차단(권한 거부·DB 불가) 등 **컨텍스트와 무관하게 이번 세션에서 진행 자체가 불가능**할 때만 별도로 중단한다. 이는 "컨텍스트가 찼다"가 아니라 "더 진행할 수 없다"는 다른 사유이며, 보고 시 그 사유를 명시한다.

- 위 1차 또는 2차 판정이 나오면 즉시 안전 경계에서 작업을 멈춘다.
  1. 현재까지 완료한 항목과 미완료 항목을 짧게 정리한다.
  2. 필요한 경우 `docs/progress/milestone-status.md`를 갱신한다.
  3. 새 세션으로 이어서 작업하라고 권유한다.
  4. 아래 재개 프롬프트를 함께 제시한다.

**새 세션 재개 프롬프트**
```text
`docs/progress/milestone-status.md`를 먼저 읽고,
현재 마일스톤 M{N}의 {현재 단계}부터 이어서 작업해줘.
마지막 완료 항목은 {파일 또는 티켓 목록}이고,
다음 작업은 {다음 작업 1개}이다.
```

**[강제] 다음 스텝 제안 시 재개 프롬프트 상시 동반**

오케스트레이터가 사용자에게 "다음 스텝 제안"을 출력하는 **모든 지점**에서, 그 제안 바로 다음에 위 **새 세션 재개 프롬프트**(단일 ```text 블록)를 **반드시** 함께 출력한다. 예외 없음.

- 적용 지점: Phase 5-C·5-D 완료 보고의 "다음 스텝 제안", 버그 경로 종료 지점, Phase R 리팩토링 완료 보고, 컨텍스트 감시 루프의 안전 중단, 그 외 다음 작업을 한 줄이라도 제안하는 모든 응답 종료부. (예외 1: 버그 경로 5번 evaluator 안 닿음 시 사용자 시각 검증 응답을 대기하는 단계 — 이때는 "응답 대기 자체"가 next-step이므로 별도 재개 프롬프트를 출력하지 않는다. 6번 긍정 응답 종료 시점에 동반 출력한다. 예외 2: Phase 5-B UI 마일스톤 사용자 검증 응답을 대기하는 단계 — 동일한 이유로 별도 재개 프롬프트를 출력하지 않는다. 5-C 긍정 응답 종료 시점에 동반 출력한다.)
- 채우는 값: "재개 프롬프트 요청 시 처리 경로" 2번과 동일한 정본을 직접 읽어 합성한다.
- 첫 줄은 `/orchestrate <다음 작업 한 줄>`로 시작하여 새 세션이 스킬에 바로 진입하도록 한다.
- 정본에 미반영된 직전 확정 설계 결정이 있으면 프롬프트에 1줄로 명시한다.
- 파일은 생성하지 않는다(정본은 milestone-status.md, DRY). 텍스트만 합성한다.

## Phase R: 리팩토링/구조 개선

리팩토링 요청은 마일스톤 파이프라인과 분리한다.

1. 오케스트레이터가 변경 목적을 구조 개선으로 한정한다.
2. `refactor-specialist`에 대상 파일, 개선 목표, 보존 동작, 제외 범위를 전달한다.
3. 구조 변경만 완료되면 `qa-guard`로 보안·컨벤션·테스트를 확인한다.
4. 동작 변경 가능성이 발견되면 `refactor-specialist`는 중단하고 상위 에이전트가 `bug-fixer` 또는 구현 에이전트로 재배치한다.
5. 요구사항 충족 변화가 의심될 때만 `evaluator`를 추가 호출한다.

## Phase 1: 마일스톤 분석

0. **계획 정합성 선점검 (마일스톤 착수 전 자동).** 요구사항 추출에 앞서 `Agent(plan-auditor)` 를 호출하여, 착수할 마일스톤의 체크리스트가 근거 문서(로드맵·audit 보고서·작업 로그)와 정합한지 점검한다. 감사 대상 마일스톤 번호와 정본 경로를 전달한다. (근거 문서가 없는 신규 프로젝트는 plan-auditor가 "대조 불가 — 근거 부재"로 빠르게 통과하므로 개입 비용이 작다.)
   - `정합성 결과: consistent` → 그대로 1번으로 진행한다.
   - 결함 발견 → 사용자에게 결함 목록과 3등급 분류를 보고한다. 잘못된 계획으로 구현에 진입하지 않는다. "문서 수정" 결함은 milestone-tracker에 위임해 정본을 바로잡은 뒤 진행하고, "재판단 필요" 결함은 사용자 결정을 받은 뒤 진행한다.
1. 프로젝트 로드맵 문서에서 해당 마일스톤 요구사항 추출 (있을 경우)
2. 작업 티켓 문서에서 세부 작업 목록 확인
3. 작업 유형 분류:
   - 원본/레거시 참조 필요 여부 → 레거시 분석 에이전트 투입 결정 (포팅 프로젝트인 경우)
   - 프론트 구현 필요 여부 → 프론트 구현 에이전트 투입 결정
   - DB/API 구현 필요 여부 → 백엔드 구현 에이전트 투입 결정
   - UI 구현 포함 여부 → **프론트 구현 에이전트가 투입되면 Phase 4에서 `design-reviewer` 자동 투입** (qa-guard 실행 전 선행)

> **마일스톤↔에이전트 매핑.** 어느 마일스톤에 어떤 구현 에이전트를 투입하는지는 프로젝트가 정의한다(로드맵·티켓 또는 별도 매핑표). 일반 규칙: ① UI가 포함되면 프론트 구현 에이전트 + Phase 4 design-reviewer, ② DB/API가 포함되면 백엔드 구현 에이전트 + Phase 2.5 tdd-agent, ③ 헤드리스(결정 문서·마이그레이션 등 사용자 가시 UI 없음)면 Phase 5-D 즉시 커밋 경로. 구체 매핑 예시는 `examples/nextjs-mysql` 참조.

원본 참조가 필요한 경우 `Agent(레거시 분석 에이전트)`를 호출한다. 분석 대상 파일 경로 또는 기능명을 입력으로 전달한다. (작업 봉투 `참조`에 `docs/compound/legacy/README.md` 의무 포함)

산출물: `_workspace/01_legacy_{feature}.md`

이후 구현 에이전트, `tdd-agent`, `evaluator`가 이 파일을 참조한다. 신규 개발 프로젝트(레거시 없음)는 이 Phase를 건너뛴다.

### 범위 축소 결정의 사용자 확인 (필수)

포팅 중 원본 요소를 구현 범위에서 빼기로 결정할 때(원본 결함·범위 조정 등 사유 불문), 그 결정이 **사용자 가시 구조 단위** — 테이블 열, 행 액션 버튼, 탭, 페이지, 메뉴 항목, 화면 섹션 — 를 제거·축소하면, 사용자에게 묻는 질문에 **구체적 before→after 구조 델타**를 명시한다.

- 나쁜 예: "원본의 깨진 요소는 어떻게 할까요?" — 카테고리 라벨만. 사용자가 가시적 결과를 알 수 없다.
- 좋은 예: "선정안내·티켓 2개 열을 빼면 원본 12열 테이블이 10열이 됩니다. 빼는 데 동의하시나요?" — before→after 델타 명시.

이유: "백엔드 메서드가 깨졌다"와 "테이블에서 열이 사라진다"는 사용자 체감 크기가 다르다. 후자를 전자 질문에 동봉하면 가시적 영향이 부각되지 않아, 사용자가 완성물을 보고서야 차이를 인지하게 된다. 이렇게 확정된 제외 항목과 승인 출처는 `_workspace/01_legacy_*.md` 또는 작업 봉투에 기록하여 Phase 4 evaluator 가 "의도적 제외 목록"으로 보고하도록 전달한다.

## Phase 2.5: TDD — 실패 테스트 작성 (백엔드 구현 에이전트 투입 시에만)

백엔드 구현 에이전트가 투입되는 마일스톤(데이터 접근·서비스·API 구현 단계)에서만 실행한다. 목업·결정 문서 단계는 이 단계를 건너뛴다.

`Agent(tdd-agent)` — 마일스톤 번호, 백엔드 구현 에이전트가 구현할 API/쿼리 목록, `_workspace/01_legacy_*.md` 경로(있을 경우)를 전달한다. (작업 봉투 `참조`에 `docs/compound/tdd/README.md` 의무 포함)

- 산출물: 데이터 접근·API 레이어의 실패 테스트 파일 (Red)
- tdd-agent는 테스트 작성 + Red 실행 확인 후 반환한다
- tdd-agent 반환 메시지의 "완료 항목"(테스트 파일 목록)을 Phase 3 백엔드 구현 에이전트 호출 시 함께 전달한다

프론트 구현 에이전트만 투입되는 마일스톤은 이 단계를 건너뛴다.

## Phase 3: 구현 (서브 에이전트 순차 호출)

실행 모드: 서브 에이전트. 각 에이전트는 격리된 컨텍스트에서 실행되며, 최종 반환 메시지만 오케스트레이터에 전달된다.

### Phase 3-0: 티켓 파싱 — 원자 작업 목록 생성 (에이전트 호출 전 필수)

에이전트를 호출하기 전에 오케스트레이터가 직접 작업을 분할한다. 이 단계를 건너뛰면 에이전트가 무엇을 누락했는지 확인할 수단이 없다.

1. 마일스톤 티켓 문서 읽기
2. **산출물** 섹션에서 모든 파일 경로 추출 (명시되지 않은 스타일·공용 컴포넌트도 포함)
3. 의존 관계 순서로 정렬:
   - 백엔드: 데이터 접근 레이어 → 서비스 레이어 → API 핸들러
   - 프론트: 공용/공유 컴포넌트 → 전용 컴포넌트 → 페이지
4. `TaskCreate`로 각 파일을 **개별 태스크**로 등록하고 태스크 ID 목록 보관

### Phase 3-1: 에이전트 호출

에이전트 호출 프롬프트에 반드시 아래 내용을 포함한다:

```
## 작업 봉투

목표:
  M{N}의 <기능명>을 검증 가능한 상태로 구현한다.

범위:
  아래 구현 대상 파일 목록만 처리한다.

제외:
  티켓에 없는 새 기능, 리팩터링, 디자인 임의 변경, 운영 DB 접근

참조:
  - 마일스톤 티켓 문서
  - _workspace/01_legacy_*.md (있을 경우)
  - 프로젝트 디자인 레퍼런스 (UI 작업인 경우)
  - docs/compound/{카테고리}/README.md (호출 에이전트별 — 카테고리가 있으면. 작업 전 필독·관련 유형 파일 로드)

완료 기준:
  - 모든 task_id가 completed 상태다.
  - 완료 항목에 실제 수정 파일을 전부 기재한다.
  - 목록에 없는 파일을 생성했으면 확인 필요에 사유를 남긴다.

구현 대상 파일 목록 (이 순서대로 처리할 것):
  [t001] ...
  [t002] ...

규칙:
- 각 파일을 구현한 즉시 TaskUpdate(task_id, status: "completed")를 호출하라
- TaskUpdate를 호출하지 않은 채 다음 파일로 넘어가지 말 것
- 목록에 없는 파일을 추가 생성했다면 완료 보고 형식의 "확인 필요" 항목에 명시하라
- 표준 반환 형식을 유지하라
```

**모델 선택 규칙**

모든 하위 에이전트는 `model: "opus"`로 호출한다. 하네스 품질은 에이전트 추론 능력에 직결되며, 에이전트 정의 파일(`agents/*.md`)도 전원 `model: opus`로 통일돼 있다. `Agent()` 호출 시 `model: "opus"` 파라미터를 명시한다.

**실행 경로**

> 백엔드 구현 에이전트 호출 시 Phase 2.5 tdd-agent가 생성한 테스트 파일 경로 목록을 함께 전달한다. 백엔드 구현 에이전트는 해당 테스트가 통과(Green)하도록 구현한다.

*API 의존 없음 — 병렬 실행:*

`Agent(백엔드 구현 에이전트, run_in_background: true, tdd 파일 목록 + 태스크 ID 목록 포함)` + `Agent(프론트 구현 에이전트, run_in_background: true, 태스크 ID 목록 포함)` 동시 호출 → 둘 다 완료 후 Phase 3-2 진행

*API 의존 있음 — 순차 실행:*

`Agent(백엔드 구현 에이전트, tdd 파일 목록 + 태스크 ID 목록 포함)` → Phase 3-2 검증 → 반환 메시지에서 구현된 API 명세 추출 → `Agent(프론트 구현 에이전트, API 명세 + 태스크 ID 목록 포함)` → Phase 3-2 검증

*프론트 구현 중 예상치 못한 API 필요 발견 시:*
1. 프론트 구현 에이전트가 `API 명세 필요` 반환 메시지로 구현 중단 (이미 완료된 파일 목록 포함)
2. 오케스트레이터가 `Agent(백엔드 구현 에이전트)`로 해당 API 구현 + 관련 태스크 등록
3. 백엔드 구현 에이전트 반환 메시지(API 명세)와 함께 `Agent(프론트 구현 에이전트)` 재호출

### Phase 3-2: 원자 작업 완료 검증

에이전트 반환 즉시 수행한다. 에이전트가 "모두 완료했다"고 보고해도 이 단계를 건너뛰지 않는다.

1. `TaskList`로 Phase 3-0에서 등록한 전체 태스크 상태 확인
2. `status`가 `completed`가 아닌 태스크 목록 추출
3. **미완료 태스크가 있으면**:
   - 해당 파일 + task_id 목록만 추출
   - 동일 에이전트를 재호출 ("아래 파일이 아직 구현되지 않았다. TaskUpdate를 포함하여 구현하라" 명시)
   - 재호출 후 TaskList 재확인
   - 동일 태스크가 2회 연속 미완료 → stuck 판정 후 에스컬레이션
4. **모든 태스크 `completed`** → milestone-tracker 갱신 → Phase 4 진행

**구현 완료 후 milestone-tracker 갱신**

Phase 3-2 통과 후 즉시 `Agent(milestone-tracker)`를 호출하여 해당 항목을 `[x]`로 갱신한다 (🔄 진행 중 처리).

**데이터 흐름**

```
오케스트레이터 → 티켓 파싱 → TaskCreate (파일별 태스크)
                                    ↓ 태스크 ID 목록
레거시 분석 에이전트 → _workspace/01_legacy_*.md
                     ↓ 참조
tdd-agent     → 데이터 접근·API 테스트 (Red)
                     ↓ 테스트 파일 목록 + 태스크 ID 목록
백엔드 구현    → 데이터 접근·서비스·API (Green) — 각 파일 완료 시 TaskUpdate(completed)
프론트 구현    → 페이지·컴포넌트 — 각 파일 완료 시 TaskUpdate(completed)
     ↓ 반환 메시지 (오케스트레이터 수신)
오케스트레이터 → TaskList 검증 → Agent(milestone-tracker) 갱신 → Phase 4 진행
```

## Phase 4: 검증

**design-reviewer(UI 마일스톤만)**, **qa-guard**, **evaluator** 순으로 호출한다.

0. **design-reviewer — 시각적 스펙 검증 (프론트 구현 에이전트가 투입된 경우만)**
   `Agent(design-reviewer)` — 프론트 구현 에이전트 반환 메시지의 `완료 항목` 파일 경로 목록을 입력으로 전달한다. (작업 봉투 `참조`에 `docs/compound/design/README.md` 의무 포함)
   - 산출물: `_workspace/design_review_{scope}_{datetime}.md`
   - 자동 수정 범위: 디자인 토큰 치환, `:hover`/`:focus` 캐스케이드 오버라이드 규칙 추가, `aria-label`/`alt` 속성 추가
   - `구현-에이전트-위임` 항목이 있으면 구현 에이전트 보완 요청 → design-reviewer 재검증을 `approved` 반환 시까지 반복. 동일 FAIL 항목 목록이 3회 연속 변화 없으면 stuck 판정 후 에스컬레이션.
   - **학습 트리거**: 동일 FAIL 항목 목록이 2회 연속 반복되면 stuck 전이라도 `Agent(compound-learner, 트리거: design-repeat, 보고서: 최신 _workspace/design_review_*.md 경로)`를 호출한다. 동일 반복 묶음당 1회만 호출한다.
   - **보완 루프 동안 qa-guard는 실행하지 않는다.** design-reviewer `approved` 반환 후에만 다음 단계 진행.
   - 프론트 구현 에이전트 미투입 마일스톤은 이 단계를 건너뛴다.

1. **qa-guard** — 코드 품질·보안·컨벤션 검증
   `Agent(qa-guard)` — 구현 에이전트 완료 항목의 파일 경로 목록을 입력으로 전달한다. (작업 봉투 `참조`에 `docs/compound/qa/README.md` 의무 포함)
   - 산출물: `_workspace/qa_{feature}_{datetime}.md`
   - 실패 항목 있으면 담당 에이전트에 수정 요청 → qa-guard 재검증을 전 항목 통과 시까지 반복. 동일 실패 항목 목록이 3회 연속 변화 없으면 stuck 판정 후 에스컬레이션.
   - **학습 트리거**: 동일 실패 항목 목록이 2회 연속 반복되면 stuck 전이라도 `Agent(compound-learner, 트리거: qa-repeat, 보고서: 최신 _workspace/qa_*.md 경로)`를 호출한다. 동일 반복 묶음당 1회만 호출한다.

2. **evaluator** — 요구사항 충족 검증
   `Agent(evaluator)` — 마일스톤 번호, 구현 파일 목록, `_workspace/01_legacy_*.md` 경로(있을 경우)를 입력으로 전달한다. (작업 봉투 `참조`에 `docs/compound/evaluation/README.md` 의무 포함)
   - 산출물: `_workspace/eval_{milestone}_{datetime}.md`
   - **의도적 제외 항목 전달 규칙**: 범위에서 뺀 원본 요소가 있으면 evaluator 작업 봉투에 "gap 판정 금지" 같은 침묵 유도 표현을 쓰지 않는다. 대신 "원본에 존재하나 제외된 항목 목록 + 각 승인 출처"를 전달하고 `evaluate` 의 "의도적 제외 목록"에 명시하라고 지시한다. evaluator 는 제외를 통과(`◐`)시키되 보고서 전용 목록에 남긴다 — 승인은 통과를 뜻하지 비가시를 뜻하지 않는다.
   - 누락/초과 항목 있으면 담당 에이전트 보완 요청 → evaluator 재검증을 `approved` 반환 시까지 반복. 동일 미해결 항목 목록이 3회 연속 변화 없으면 stuck 판정 후 에스컬레이션.
   - **gap이 발견된 경우** (미승인 또는 재검증 통과 불문): 최종 결과 확정 후 `Agent(compound-learner, 트리거: eval-gap, 보고서: eval 파일 경로)` 호출

## Phase 5: 사용자 검증 + 완료 보고

evaluator `approved` 반환 후 마일스톤을 곧바로 ✅ 처리하고 커밋하지 않는다. **프론트 구현 에이전트가 투입된 UI 마일스톤**은 자동 커밋 직전에 사용자 시각/기능 직접 검증 게이트를 반드시 통과시킨다. evaluator 는 코드 차원 정합성을, 사용자는 시각/기능 차원 정합성을 각각 보증한다 — 두 보증이 합쳐져야 진짜 완료다. 흐름은 `5-A → (5-B → 5-C) 또는 5-D` 이며, 부정 응답은 `5-E` 보완 회귀로 빠진다.

> **evaluator 미승인 시 처리**: Phase 4 evaluator 가 미승인 반환했다면 5-A 로 들어오지 않는다. 해당 에이전트 보완 요청 → evaluator 재검증을 `approved` 반환 시까지 반복한다. approved 후에만 Phase 5 진입.

### Phase 5-A: 적용 범위 판정

이번 마일스톤 파이프라인에 프론트 구현 에이전트가 한 번이라도 투입됐는지를 본다. 판정은 Phase 3 호출 기록만으로 수행 — 코드 변경 분석 같은 의미 판단은 금지.

- **프론트 구현 에이전트 투입됨** (UI 마일스톤) → 5-B 사용자 검증 게이트
- **프론트 구현 에이전트 미투입** (DB 레이어·결정 문서·마이그레이션 등 헤드리스 마일스톤) → 5-D 즉시 커밋 경로

### Phase 5-B: 사용자 시각/기능 검증 게이트 (UI 마일스톤)

1. **검증 요청 보고서 출력** — 사용자가 무엇을 확인해야 하는지 구체적으로 명시한다. 단순히 "확인 부탁드립니다"는 금지.
   - 구현된 파일 목록
   - qa-guard 결과 요약 (PASS/FAIL 항목)
   - evaluator 결과 요약 (충족/누락/확인 필요)
   - **원본 대비 의도적 제외 목록 재노출**: evaluator 보고서의 "의도적 제외 목록"이 비어있지 않으면 그 표를 그대로 옮기고 "원본과 달라지는 부분입니다 — 의도와 다르면 알려주세요" 를 덧붙인다. 작업 시작 시점의 추상적 승인을 완료 시점의 구체적 재확인으로 보완한다.
   - **확인 요청 항목**: 사용자가 브라우저에서 점검할 URL 경로 + 재현 시나리오
   - **응답 게이트 명시**: "이번 변경을 브라우저에서 확인 부탁드립니다. 긍정 응답 후에 milestone-tracker ✅ + 자동 커밋을 진행합니다. 재발 방지 학습(compound-learner) 도 사용자 응답 후 수행됩니다."
2. **사용자 응답 대기** — 이 시점에서는 milestone-tracker ✅ 미갱신, 커밋 미실행, compound-curate 드레인 미발동. 그리고 **재개 프롬프트도 출력하지 않는다** (응답 대기 자체가 next-step).
3. **다음 턴 분기**:
   - **긍정 응답** ("확인됨", "오케이", "잘 됨", "통과" 등) → 5-C 진입
   - **부정/미해결 응답** ("X가 안 됨", "Y가 깨짐", "이 부분 누락" 등) → 5-E 보완 회귀
   - 응답이 모호하면 사용자에게 "긍정 처리해도 될까요, 보완이 필요할까요?" 1회 확인 후 분기

### Phase 5-C: tracker ✅ + 커밋 + 보고 (UI 마일스톤 긍정 경로)

1. **milestone-tracker 최종 갱신** — `Agent(milestone-tracker)` — `phase-4-eval approved + 사용자 검증 통과` 신호 전달
   - 산출물: `docs/progress/milestone-status.md` ✅ 완료 처리
2. **자동 커밋** — `Skill(commit)` 호출 (린트 검사 + 커밋)
   - 커밋 메시지 형식: `feat(M{N}): {마일스톤 슬러그 한 줄 요약}`
   - 커밋 실패 시 사용자에게 알리고 수동 커밋을 안내한다
3. **compound-curate 드레인 (커밋 직후)** — Phase 0 "재발 방지 학습 푸시"에서 적재된 curate-needed 세션 메모 목록이 비어 있지 않으면, `Agent(compound-learner, 트랙: compound-curate, 대상: curate-needed 플래그 목록, run_in_background: true)` 를 호출. 학습 4트랙과 달리 evaluator `approved` 와 무관하며, 커밋 직후이므로 후속 tracker·commit 호출이 없다. 결과는 4번 보고에 1줄 요약. 플래그가 비어 있으면 이 단계를 건너뛴다.
4. **사용자 최종 보고**:
   - milestone-tracker 갱신 결과
   - 자동 커밋 결과 (커밋 해시 포함)
   - compound-curate 드레인 결과 1줄 요약 (드레인이 발동된 경우만)
   - 다음 스텝 제안
   - **[강제] 다음 스텝 제안 직후 새 세션 재개 프롬프트(단일 ```text 블록)를 반드시 동반 출력한다.**

### Phase 5-D: 비-UI 마일스톤 즉시 커밋 경로 (프론트 구현 에이전트 미투입)

사용자가 브라우저에서 시각 확인할 대상이 없으므로 사용자 검증 게이트를 두지 않는다. 흐름은 5-C step 1→2→3→4 와 동일하되 검증 요청 보고서(5-B step 1) 는 생략하고 곧바로 진행한다.

1. `Agent(milestone-tracker)` ✅ (evaluator approved 신호)
2. `Skill(commit)`
3. compound-curate 드레인 (5-C step 3 동일, background)
4. 사용자 보고 (구현된 파일 목록·qa-guard·evaluator 결과·**의도적 제외 목록 재노출(있을 때)**·tracker 갱신·커밋 해시·드레인 요약·다음 스텝·**[강제] 재개 프롬프트 동반**)

### Phase 5-E: 보완 회귀 (사용자 부정 응답)

1. **응답 본문 분류 — 오케스트레이터 자동 분류.** 사용자 응답에서 결함 성격을 읽고 보완 에이전트를 선택한다.
   - **동작 결함** (특정 기능이 안 됨, 에러 토스트, 데이터 안 보임, 클릭 무반응) → `Agent(bug-fixer)`. 사용자 응답 본문(증상·재현 경로·스크린샷 언급)을 `진단 맥락` 으로 전달.
   - **시각 결함** (스타일 깨짐, 토큰 미반영, hover/focus 잔재, 레이아웃 어긋남) → `Agent(bug-fixer)` (bug-fixer 가 스타일/마크업도 처리)
   - **마일스톤 스펙 누락 항목** (티켓에 있던 X 가 화면에 없음) → 해당 구현 에이전트에 보완 요청. 작업 봉투 `참조` 에 사용자 응답 본문 첨부.
   - **추가 기능 요청** (티켓 범위 외) → 신규 티켓 분리 권고. 사용자에게 "마일스톤 범위 외 기능으로 보입니다 — 신규 티켓 분리 후 별도 작업이 적절합니다. 현 마일스톤은 이대로 ✅ 처리해도 될까요, 아니면 보류할까요?" 결정 요청.
   - **분류 모호 시** 사용자에게 "어디 계열 보완일까요? [bug-fixer / 프론트 구현 / 백엔드 구현 / evaluator 재검증]" 1회 분류 확인 후 진입.
2. **보완 → 재검증 사이클** — 보완 에이전트 호출 후 Phase 4 evaluator 재검증 → approved 시 5-A 회귀 (다시 사용자 검증 게이트 진입).
3. **반복 학습 트리거** — 동일 미해결 항목 2회 연속 반복 시 `Agent(compound-learner, 트리거: user-verify-repeat, 보고서: 사용자 응답 본문 + 보완 시도 이력, run_in_background: true)` 를 호출한다. 동일 반복 묶음당 1회만 호출한다.
4. **stuck 판정** — 동일 미해결 항목 3회 연속 변화 없으면 stuck 판정 → 에스컬레이션.
5. **compound-learner 봉투 주석** — 2회 이상 재보완이 누적된 끝에 사용자 긍정 응답을 받으면, 1차·2차 가설과 정진단 흐름을 compound-learner 봉투에 함께 전달하여 자매 보존 vs `_superseded` 격리 판단을 맡긴다.

## 에러 핸들링

상세 규칙(보완-재검증 루프 전략, stuck 감지, 에스컬레이션 기준)은 `references/error-handling.md`를 읽어 따른다.

**요약**
- 에이전트 실패 시 1회 재시도, 재실패 시 보고서에 명시하고 계속 진행
- 동일 미해결 항목 2회 연속 → compound-learner 호출 (학습)
- 동일 미해결 항목 3회 연속 변화 없음 → stuck 판정 → 에스컬레이션
